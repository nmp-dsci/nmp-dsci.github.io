nmp-dsci.github.io · build console · admin runbook

You run it with one command.
You update it by editing one file.

This documents the recommended backend from the options page — Markdown per project (Jekyll collection). There is no server, no database, no deploy pipeline to babysit: the git repo is the backend, and GitHub Pages rebuilds the site automatically every time master changes. If you pick a different backend on the options page, tell me and I'll redraw this.

00

The mental model — four things, cleanly separated

Content · you, often

_projects/*.md

One Markdown file per project. Front-matter feeds the cards and grid; the body is the case-study page. Adding a project = adding a file.

Look · rarely

_layouts/ · _includes/ · assets/css

Templates and styles every project shares. Restyle here once, every page changes. You mostly never touch these — or ask me to.

Builder · automatic

GitHub Pages

Runs Jekyll on every push to master and publishes the result. Nothing to configure after the first setup, nothing to maintain.

Production · = master

nmp-dsci.github.io

Whatever is on master is the live site, usually within a minute of merging. Branches (like portfolio-rebuild) are free staging.

04

Runbook — the three commands that matter

once, ever

Set up local preview

Needs Ruby ≥ 3.1 (macOS system Ruby is too old — rbenv shown). Skip entirely if you're happy previewing via branch + editing on github.com or through me.

each edit session

Run the site locally

One command. Serves at http://127.0.0.1:4000, rebuilds and reloads the browser on every save.

to publish

Commit → merge to master

Push to portfolio-rebuild to stage; merging to master is the deploy. Pages rebuilds automatically — no other action exists.

runbook.sh· the full admin surface, top to bottom

No-setup path

Edit _projects/*.md directly on github.com from any device — commit in the browser, Pages rebuilds. No Ruby, no clone.

Agent path

Tell me the change in plain English. I edit, serve you a live preview to annotate (this loop), then commit what you approve.

Safety net

Pages publishes master only — anything on a branch is invisible to visitors, and git revert un-ships a bad merge in seconds.

06

Facts worth pinning

No CI to maintain. GitHub Pages runs Jekyll itself on every push to master — the build step is GitHub's problem, permanently.
Merge = deploy. There is no second publish action. If a page looks wrong live, check the repo's Pages/Actions tab for the build, or just revert the merge.
Content never breaks design. Write-ups are Markdown; templates render them. You cannot corrupt the site's look from a content edit.
Everything is versioned. Every write-up edit is a commit — full history, diffs, and rollback for free, because the backend is git.
