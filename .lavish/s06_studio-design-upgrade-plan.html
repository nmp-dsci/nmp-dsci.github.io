The three real gaps

  1. No anchor display face. Every heading on the site is IBM Plex Sans 600. It reads competent and completely interchangeable with every other engineer portfolio.
  2. No layout variation. Below the hero the home page is four grid sections in a row.
  3. No scan layer. The home page asks a 60-second visitor to read three 60-word paragraphs at 14px.

All three are fixable without a new font file, a new colour, or a new dependency.

The three changes you asked for

These ship together as one change. They are additive, they touch no colour token, and they cannot break the contrast audit. Two of the three are also s20 advice — wayfinding is what "people scan, they don't read" looks like in a navigation bar.

A2 · requested

A "Case studies" dropdown in the nav

Today the nav's first link is Work, which scrolls to /#work. From a case-study page there is no way to reach a sibling case study without going home first. The dropdown fixes that and, in the site's idiom, carries its evidence: each entry shows the system's rubric score, so the menu itself argues the case.

How it is built

Markup
A native <details class="nav-drop"> with a <summary>. Keyboard support, aria-expanded and the no-JavaScript fallback all come free from the element — no ARIA menu pattern to get wrong.
Source
The same Liquid query the home page already uses: site.projects | where production.live | sort production.order. It cannot drift from #work, and it can never surface the six unpublished projects.
JS
~10 lines: close on outside click and on Escape. Everything still works with the script removed.
Motion
Opacity + 4px rise over --dur, so it inherits prefers-reduced-motion like everything else.
Mobile
Inside the existing .nav-links sheet the panel renders inline and indented instead of floating — no second overlay to manage.

One decision embedded here: the nav item is renamed Case studies, not kept as Work. "Work" is a portfolio word; "case studies" says what the pages actually are and matches the kicker already printed on every one of them (RAG · CASE STUDY).

A3 · requested

A page tree

The site has no sitemap, no /404 and no index of itself. A page tree is the cheapest possible answer to "how big is this, and what else is here?" — and rendered in Plex Mono it is on-brand rather than bolted on, because mono is already the site's voice for structure and data.

footer · every page

generated from the collections — never hand-maintained

Why the footer

It is present on all eight pages at zero navigation cost, it is where a hiring manager already looks for links, and it gives the footer — currently one thin line of text — a reason to exist. A dedicated /map/ page would be a page nobody visits; the case-study rail is already carrying a TOC and a readiness card.

Like the dropdown it is generated from the collections, so the three systems, their rubric scores and the three practices stay correct on their own. It collapses to a single indent level under 560px.

This one is a genuine choice — placement changes what the tree is for. Three options are laid out in the decisions section below.

Part three

The s20 upgrades worth making

Seven changes, ordered by impact per hour. B1 is the one that changes how the site feels; the rest are corrections. None of them adds an asset, a dependency or a colour.

B1 · the big one

Give the site an anchor display face

s20's first typography lever: anchor on the headline font, not the body — it sets the page's whole personality. Every heading here is IBM Plex Sans Semibold, which is exactly the face a hiring manager has seen on the last forty engineer portfolios. Meanwhile IBM Plex Serif is already downloaded, already preloaded, and already on the page — it is what the dek and the case-study prose are set in, and it is the more distinctive voice of the two.

The change is to invert the pairing: serif for display, sans for interface. It costs zero bytes — serif-normal-600.woff2 (15.6 KB) and serif-italic-400.woff2 (16 KB) already ship and are already in the preload list.

now · plex sans 600
I ship gen-AI systems and prove they're production-ready.

Three systems live on AWS — each with evals in CI, guardrails between the model and the data, per-request traces and cost caps.

reads: correct, competent, interchangeable

proposed · plex serif 600 + one italic keyword
I ship gen-AI systems and prove they're production-ready.

Three systems live on AWS — each with evals in CI, guardrails between the model and the data, per-request traces and cost caps.

reads: authored, specific, field-guide

Scope: h1, h2 and the case-study .page-head h1 move to var(--serif). h3, all UI, all labels and every button stay sans — that is what makes it a three-tier hierarchy with distinct treatment rather than a font swap. Mono is untouched.

This contradicts DESIGN.md §2, which currently reads "IBM Plex Sans for display and UI, IBM Plex Serif for reading". The brief says a disagreement means the brief is wrong — fix it, but it is your identity, so it is a decision, not an edit. See D1 below.

B2

One decorated keyword per page

s20: decorate one keyword — singular emphasis, never scattered. The CSS hook already exists (.hero h1 em) and nothing uses it. Add <em> to exactly one word in each h1: prove on the home page, prove on Transcript RAG, refused on ConvFinQA, governed on Data Pilot. One per page, enforced by a line in the case-study lint.

Files site.yml, 3 × _projectsRisk none Effort ~30 min

B3

Fix the hero's balance

The hero grid is 1.05fr / 1fr with align-items:center, which leaves roughly 150px of dead space above the kicker while the matrix runs the full height. s20: 60/40 beats 50/50; balance is not symmetry. Change to align-items:start and a genuine 56/44 split, and let the h1 breathe to 18ch. Two declarations.

Files main.cssRisk none Effort ~30 min

B4 · the scan layer

Stop asking the home page to be read

s20 is blunt: people scan, they don't read. Each system row currently prints a ~60-word DEMO paragraph and a RUNS ON line at 14px — about 200 words of dense small text inside the first two screens, all of it repeated verbatim on the case study a click away. It is the least scannable thing on the site and there are three of it.

Now · per system row

headline · one-sentence outcome · DEMO: 60 words · RUNS ON: 25 words · rubric count · two CTAs · architecture diagram

≈ 110 words per row, ×3

Proposed

headline · one-sentence outcome · three fact chips (rubric · region · monthly cost) · two CTAs · architecture diagram · the demo detail behind a disclosure

≈ 35 words per row visible; nothing deleted

No content is lost — the demo paragraph moves into a <details> labelled "what you can actually do in the demo", which also makes it honest: the visitor opens it because they want it, not because it was in the way. The RUNS ON line becomes three mono chips, which is what it already is semantically.

Files system-row.html, main.cssRisk low Effort ~2 h

B5

Break the four-grid monotony

Below the hero the page is: stacked rows → 3×3 grid → 3-up grid → 3-up grid. s20: vary the layout as the page progresses — but only variation with a purpose. Two purposeful changes: split the nine rubric dimensions into the learning half (R1–R4) and the operating half (R5–R9) as two labelled columns — a distinction the page's own lead paragraph already makes but the layout hides; and run the scale ladder as a left-to-right progression with the deployed rung visually anchored, since 10 → 100 → 1,000 is a sequence, not three peers.

Files rubric-dims.html, scale-ladder.html, main.css Risk lowEffort ~2 h

B6

One signature moment, in the site's own register

s20 wants a scroll-stopper per page; DESIGN.md bans parallax, 3D and autoplay. Both can be satisfied by animating the thing that is already the best asset: the diagrams. On first view only, stroke-draw the rubric-loop figure and stagger the matrix cells in at 30ms intervals. It reads as craft, it uses the existing --dur, and prefers-reduced-motion disables it by changing one token. Nothing moves on scroll; nothing repeats.

Files main.css, ~20 lines JSRisk low Effort ~2 h

B7 · durability

Make the design audit repeatable

s20's prompt #09 is the pre-launch audit, re-run until the score clears the bar. The site scored 137/145 once, by hand, in the s05 artifact — which means the next change can quietly undo it and nothing will say so. Add .claude/skills/design-audit/ holding the twelve-dimension rubric and DESIGN.md's never-list, so "audit the site" is one command that returns a scored, comparable report. The contrast audit already proves this pattern works; this extends it from colour to composition.

Files new skillRisk none Effort ~1 h

Part four

What I am deliberately not taking from s20

s20 is a general guide for building marketing sites with agents. A good half of it is either already banked here or actively wrong for a portfolio whose whole argument is restraint. Recording the rejections so they do not get re-litigated in six weeks.

✕Hero video, generated imagery, a scroll-scrubbed focal image. DESIGN.md rule 7: the rubric matrix is the hero image. The evidence outperforms any picture we could generate, and s20's own warning applies — "the most enthralling site reviewed was also the least comprehensible".
✕Count-up numbers and animated statistics. You already cut the three-metric strip in the last round ("they suck as wins"). Animating numbers would reintroduce the pitch-deck register through the back door.
✕Reference-and-mold from an award site. s20's strongest anti-generic technique, and the wrong tool here: this site's distinctiveness should come from the evidence being real, not from wearing another studio's clothes. B1 buys the same distinctiveness from a font that is already on the page.
✕A 5–7 page sitemap derived from niche research. The page count is already correct and deliberately small. The page tree (A3) is the part of that advice that applies.
✕Shader effects, three.js, cursor-following 3D, spring physics. Ruled out by the motion section of the brief, and every one of them is a speed tax on a page whose visitor is scanning for 60 seconds.
✕Component libraries and design-system extraction from a reference brand. tokens.css is already a real design system with CI enforcement — stricter than what s20 asks for. Importing another would be a regression.
✕The whole of s20 Parts 2, 5 and 6 — pipeline, org design and the prompt library. That is how to build sites with agents, not what to change on this one. Worth keeping as process reference; nothing to ship.

Checks every phase must pass

  • contrast_audit.py — 50 pairs, both themes. No phase adds a colour, so this should stay at 0 failing throughout.
  • lint_case_study.py --all --no-net — plus the new one-keyword rule in Phase 1.
  • Jekyll build in the Docker image.
  • Measured sweep across 8 pages × 2 themes × 390/768/1280: 0 nodes under 12.8px, 0 horizontal overflow, 0 SVG label overflow — the same sweep the last redesign passed.

Risks, honestly

  • B1 is a taste call, not a correctness call. Serif display is warmer and more authored; it is also slightly less "systems engineer". If you want the site to read colder, keep the sans and take everything else — the plan still works.
  • B4 hides content behind a disclosure. Anyone who wanted the demo detail on the home page now needs a click. I think that trade is right for a 60-second scan; it is reversible in one commit if it isn't.
  • B6 adds the site's first animation. Small blast radius — it reads --dur, so reduced-motion already disables it — but it is new JS on a page that currently has almost none.
  • A1 leaves prose to rewrite. "an applied AI engineer in Sydney" in about.md needs a human sentence, not a find-and-replace. Flagged in D3.
