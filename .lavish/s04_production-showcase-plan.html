The rubric — what "production gen-AI" has to answer D2 LOCKED · NINE

Nine dimensions, each phrased as the question a hiring engineer would ask. This becomes _data/rubric.yml — one source of truth for the home-page matrix and every case study's "Production readiness" section, exactly like _data/skills.yml feeds the skill chips today.

R1 · evals

Evals & golden set

Is there a versioned golden set, and can anyone reproduce the score offline?

Without a fixed set the accuracy number is an anecdote. Committed predictions make the number a fact.

R2 · judge

LLM-as-judge

Who grades the open-ended answers, and is the judge independent of the model being graded?

Self-grading inflates scores; a frozen rubric and a cross-family judge keep it honest.

R3 · gate

Regression gate

What stops a worse version from shipping?

A CI gate on the eval floor — and on per-case pass→fail flips, since a better average can still hide regressions.

R4 · loop

Learning loop

How does the system get better — and is each change traceable to one lever?

Versioned prompts, diagnose → propose → verify, champion/challenger promotion, documented cycles including the failed ones.

R5 · guardrails

Guardrails & security

What sits between the model and anything it can touch — data, tools, money, other users?

Deterministic gates (RLS, AST guards, sandboxes, policy tables), abuse limits, red-teamed and regression-tested.

R6 · trace

Observability & tracing

Can you replay exactly what the agent did on one request, and see the fleet's health on one screen?

Per-run traces + SLOs with error budgets; the dashboard signal is what tells you when to scale.

R7 · cost

Cost tracking & control

What does one answer cost, what caps the worst day, and what's the cheap-by-default tier?

Cache-adjusted cost per answer, daily caps, flash-tier defaults, and a demo mode whose worst case is a fixed ceiling.

R8 · release

Deploy & release

Is a merge a deploy — and does the deploy prove the live URL is what it claims?

IaC, keyless OIDC CI/CD, a smoke test that asserts demo mode and refuses writes, and a rollback path.

R9 · scale

Scale path

What's the topology today, what's been measured under load, and what changes at 100 / 1,000 concurrent users?

Load tests, a queue-scaling experiment with a formula that held, and an honest "designed, not built" for the next rungs.

The scale ladder — 10 / 100 / 1,000 concurrent users D3 LOCKED · SHARED

Re-based on concurrent users as you asked. The ladder becomes its own practice page (_practices/production-scale.md), is summarised in one strip on the home page, and each case study shows its rung and links here. Only rung 10 is deployed; rung 100's sizing is measured (Data Pilot's queue experiment and k6 runs, on one laptop); rung 1,000 is design. The page labels each rung that way, and dollar ranges are labelled order-of-magnitude estimates.

Rung 10 · deployed

10 concurrent users — today's demo

~$5–18 / month per app · ≈ hundreds of visitors a month
  • Compute: one App Runner instance per service (front door and compute bundled); max_concurrency 100 for read paths; ConvFinQA caps live turns at 4 in flight and needs --workers 1.
  • State: sessions, rate limits and the demo pack live in process memory — correct at N=1, the named seam beyond it.
  • Data: Aurora pauses when idle (first visitor waits ~30s, narrated in the UI); the other two bake their index/CSVs into the image.
  • Spend: no inference on the public URL; worst-case bill is a fixed ceiling.
Signal to move: App Runner 5xx alarm or concurrency at cap; Aurora ACU pinned at max; in Data Pilot the deck's wait p95 rising while service p95 stays flat.
Rung 100 · sizing measured, not deployed

100 concurrent users — live LLM back on

≈ $0.5–1k / month + inference · ≈ 5–10k monthly users (1–2% concurrency rule of thumb)
  • Terms, so the diagram reads right: ALB (Application Load Balancer) is the front door — the job an API Gateway would otherwise do. ECS Fargate is the compute — where the FastAPI containers run, no servers to manage. They're the two halves of what App Runner bundles at rung 10.
  • Why ALB, not API Gateway, for the chat path: API Gateway's integration timeout is ~30s, which can't hold a 90s agent answer or an SSE stream; ALB's idle timeout goes to 4,000s. API Gateway earns a place beside the ALB only for keyed surfaces (Data Pilot's dpk_ webhook/MCP keys) where per-key usage plans and throttling are the point.
  • The sizing is arithmetic: the measured formula — drain time ⌈N ÷ slots⌉ × S — held within 6%. 100 askers × ~90s answers with a sub-3-minute wait target → ~50 slots, e.g. 8–12 worker tasks × 4–6 concurrency. Measured footprint: ~300–840 MB per warm worker, ~1.45 GB for one process running 4 slots — so ~10 tasks at 1 vCPU / 2 GB.
  • State out of process: Redis for sessions/limits — ConvFinQA's named seam; Data Pilot's queue already does this.
  • Data: Aurora min ACU > 0 kills the cold start; one reader for Explore/SQL; pgvector stays in-DB.
  • Guardrails scale with it: per-user daily caps become tenant quotas; WAF + edge rate limits; provider quota alarms — 50 concurrent LLM calls is where a single provider's rate limit starts to matter.
Signal to move: queue wait p95 rising with service p95 flat = add slots; both rising = the agent got slower (an eval problem, not infra); reader CPU / connection count on Aurora; cost-per-answer × volume crossing the budget alarm.
Rung 1,000 · designed only

1,000 concurrent users — multi-tenant fleet

≈ $5–15k / month + inference · ≈ 50–100k monthly users
  • Compute: separate autoscaling fleets per role — API, LLM-wait workers (cheap, high concurrency), CPU-bound sandbox workers, an online judge — across AZs. ~500 slots for 1,000 askers at the same wait target; slots are slots — the experiment showed one process × 4 coroutines beat 3 serial replicas.
  • Queues per class: interactive vs batch vs eval-sample, so a report backfill never queues a live user.
  • Data: Aurora writer + readers; marts partitioned by tenant/dataset; RLS graduates to schema-per-tenant where a customer demands physical isolation; pgvector to a dedicated or partitioned store.
  • LLM: 500 concurrent calls exceeds one provider's default quota — a router across providers with per-tenant quotas, prompt caching and fallbacks: the choke-point pattern ConvFinQA already has, fleet-wide.
  • Release: blue/green via ALB weighted target groups, canary judged by the online eval sample before 100%.
  • Cost: per-tenant showback; the budget alarm becomes a per-tenant quota.
Signal to move: rung-100 autoscaling hitting its max repeatedly; reader lag / connection exhaustion; one tenant's load starving others (the argument for per-class queues and sharding); provider 429s.

_practices/eval-loop.md

The eval loop

How a gen-AI system gets better without getting worse: golden set → graders + judge → gate → ship → traces → diagnose → next version → promote. The R1–R4 half of the rubric as one story, with the three systems as three instantiations.

  • Data Pilot: goldens authored in-product, build fingerprints, three documented cycles — one refused (docs/evals/cycle-002.md).
  • ConvFinQA: prompts as versioned code, GEPA → v2, s7 harness → v3.1, champion/challenger registry that refused v3.1 on per-question flips.
  • Transcript RAG: chunk-labelled goldens, 8-config ablation, RAGAS + depth-v2 judge, rejudge, 17 committed runs gated in CI.
  • Failure modes named: self-grading, a better average hiding flips, unlabelled goldens, "held-out" that isn't (ConvFinQA's 78-of-120 split disagreement).
May also cite (GitHub links only — those pages are unpublished): V2V's 9/9 red-team graded on bank state, CUAD's 10,250-prediction grid with retrieval measured separately.
_practices/ways-of-working.md

Ways of working: Git · Lavish · no-mistakes

How the three systems were built by one engineer with agents, without the usual slop: plan in the browser, build on a branch, validate through a gate, ship on merge. Three sections (or three pages — D4c).

  • Git: feature branch + PR per slice — 33 PRs merged on Data Pilot, 12 on Transcript RAG, 4 on ConvFinQA; conventional commits (Data Pilot: 71 feat · 35 fix · 16 docs); worktrees for isolated fixes (worktree-prod-login-fix); CI on every PR, deploy on merge via OIDC, "never ship a red main".
  • Lavish: every non-trivial change starts as a numbered review artifact — .lavish/sNN_*.html — architecture, plans, tickets, experiment results, screenshots — reviewed and annotated in the browser before code exists. 40 on Data Pilot, 20 on Transcript RAG, 4 on ConvFinQA, 5 here (this plan is s04). Never gitignored, by workspace rule.
  • no-mistakes: a local gate that runs intent → rebase → review → test → document → lint → push → PR → CI before anything reaches main; its findings land as no-mistakes(review|document|lint|test): commits — 27 on Data Pilot (10 review · 10 document · 4 lint · 3 test), 16 on Transcript RAG, 6 here. The benefit is the governance: the model cannot touch what the user cannot, every answer carries the SQL that produced it, and the same pipeline serves the web app, a Slack bot, a webhook and an MCP surface.

  • In the live demo: no login — Explore + the SQL editor run live against the real marts; chat replays recorded agent runs (plan → charts → report in ~5–10s); the Ops deck, Evaluations and Golden Examples are visible read-only. 2 · Agent architecture AGENTS · LLM · TOOLS · MEMORY

Agent structure — assets/img/agent/data-pilot.svg · from architecture.diagram · same figure as the home card

  • Agents: one pydantic-ai loop that plans extract → sandboxed pandas analysis → report, plus an isolated title agent (POST /agent/title) so titling never adds latency to an answer.
  • LLM: DeepSeek by default; Claude reachable behind the same abstraction (Decision G); a deterministic NL→SQL stub with no key at all, so the whole product is testable for free. Claude is used only as the eval judge.
  • Tools: schema knowledge grounded in the dbt manifest, value lookup, per-user memory (remember / recall over pgvector, embedded locally with fastembed bge-small), make_chart, and the Pyodide sandbox.
  • Prompts & skills: versioned; every answer carries a build fingerprint of provider + model + prompt / skills / knowledge hashes (agent/version.py).

3 · Agent loop & evaluation ONE REQUEST · THEN THE EVAL LOOP

  • One request: sign in → POST /ask → the backend sets app.current_user_id so RLS scopes everything → the agent recalls memory, plans, writes a single read-only SELECT → guard → run → sandbox analysis → report pages stream back over SSE as they land → the full trace and pages persist to query_runs.
  • Golden set: goldens authored in the product stage by stage (① SQL extract → ② sandbox objects → ③ report), version-controlled to evals/cases/*.yaml across three datasets on a T1–T7 question ladder.
  • Graders & judge: deterministic graders G1–G4; insight judged cross-family (Claude grades DeepSeek) against a frozen, hashed rubric — the judge refuses its own family and records skipped rather than a fake score.
  • Gate: make eval-compare blocks on any case flipping pass → fail, whatever the average does; a zero-LLM pack lint gates every merge.
  • Learning loop: make eval-diagnose proposes one-lever hypotheses from traces; three cycles written up — 001 PASS, 002 FAIL (not shipped), 003 PASS.

4 · Deployed architecture AWS · API · DATABASE · DEPLOY · SCALE

Deploy topology — assets/img/production/data-pilot.svg · from production.topology_diagram · only here, never on the home card

  • API: backend-api (FastAPI) public on App Runner — auth, RLS context, /ask, Explore, SQL editor, admin, and the non-UI front doors (webhook, Slack slash command + @mention bot, MCP at /mcp) all through one run_question(); data-agent is a second private service (token-guarded) that the demo deployment omits.
  • Database: Aurora Serverless v2 Postgres 16 + pgvector, scale-to-zero (0–1 ACU in demo); schemas app / raw / staging / marts; RLS policies and per-role statement timeouts applied by Alembic migrations; dlt + dbt build the marts as ECS Fargate one-shot jobs streaming the full CSVs from S3.

5 · Guardrails & security WHAT SITS BETWEEN THE MODEL AND THE DATA

  • Google OIDC → role gating → Postgres RLS set per request; the agent connects as a read-only role — a bug in app code still cannot leak rows.
  • Generated SQL: shape check → keyword denylist → sqlglot AST walk rejecting DML/DDL, set_config, pg_read_file and friends; analysis code runs in Pyodide/WASM (no network, no filesystem); attempt budgets, row caps, statement timeouts.

  • Tested two ways: a deterministic injection suite in CI (found two real guard defects) and a four-class promptfoo red-team (rls-bypass, jailbreak-to-dml, prompt-injection, pii-exfil) whose pass rates light the Ops deck.

6 · Observability & cost IS IT HEALTHY, SAFE, FAST, AFFORDABLE

The case-study contract — a reusable template, and a skill that fills it

Straight answer to your question: not yet. Today the structure is implicit — a layout (_layouts/project.html), a front-matter convention, and a paragraph in the readme. This section makes it explicit and reusable in three layers: a contract (schema + spine + rules), a scaffold you copy, and a /case-study skill that produces a case study from a repo, draws the two diagrams, and lints the result. The three production case studies are then built through the skill, which is the proof the template works (D9).

Layer 1 · contract

What every case study must have

Front matter (schema): title · summary · tldr · tags · metric + metric_label · featured · order · stack · skills (keys in _data/skills.yml) · skills_detail[{skill, proof}] · links{repo, demo} · media{walkthrough, poster, captions, reel} · architecture{diagram, caption} · production{live, order, surface, topology, topology_diagram, region, rung, rung_note, score, rubric[9]{dimension, status, how, proof}} · evidence[].

Body spine (H2s, in order — your structure): 1 Purpose & benefit (problem, who it's for, the benefit in one number, what you can do in the live demo) → 2 Agent architecture (agents/stages, LLMs and tiers, tools, retrieval, prompts, memory; agent-structure diagram) → 3 Agent loop & evaluation (one request end to end, then golden set → graders/judge → gate → learning loop) → 4 Deployed architecture (topology diagram; API surfaces, database/storage, CI/CD + smoke, region and sizing, scale rung) → 5 Guardrails & security → 6 Observability & cost → 7 Production readiness scorecard (rendered from front matter; each row links to its section).

Rules: every number has a repo path · all nine rubric dimensions present, statuses from the vocabulary · ◐ / ○ / — carry a reason in how · links.demo must answer mode: demo (or 200) · two diagrams: agent structure (card + §2), deploy topology (§4 only) · the seven H2s in order, none skipped (write "n/a — why" rather than omit) · summary ≤ 2 sentences, tldr = one line.

Practices get a parallel contract: title · summary · order · systems[] · rubric[] (dimensions explained) and the spine Problem → Pattern → In the three systems → Evidence → Failure modes.

Layer 2 · scaffold

_templates/ — copy, fill, lint

  • _templates/project.md — the full front matter with every key present and a one-line comment saying what goes there and where to find it in a repo (README §, infra/, .github/workflows/, evals/, SECURITY.md…), plus the seven H2s with a prompt under each (e.g. §2: "agents / stages · LLM(s) and tiers · tools · retrieval · prompts · memory").
  • _templates/practice.md — same for practices.
  • _templates/agent-structure.svg — the node/edge style used in §06 (currentColor, theme-aware, <title> on every node, viewBox 320×100) with placeholder nodes: input → stages → output → grading caption.
  • _templates/topology.svg — same style for the deploy diagram: front door → compute → data → external, with a region/cost caption.
  • readme.md §Adding a project points at the templates and the skill instead of describing the fields by hand.
Layer 3 · skill

/case-study <repo-path>

A project skill at .claude/skills/case-study/SKILL.md in this repo (versioned with the site; D8 for location). Invoked with a sibling repo path; steps:

  • Survey the repo — README, AGENTS/CLAUDE.md, infra/, .github/workflows/, evals/, tests/, SECURITY.md, .lavish/, git log — and collect facts with paths. No claim without a path.
  • Fill _templates/project.md → _projects/<slug>.md, all seven sections; skills and rubric keys must resolve in _data/.
  • Score the nine rubric rows — status + how + proof; anything below ● gets its reason.
  • Draw the two SVGs from the templates into assets/img/agent/ and assets/img/production/.
  • Lint with scripts/lint_case_study.py --repo <path> and build with bundle exec jekyll build.
  • Review — open the draft in Lavish (the practice), then commit on a branch and run no-mistakes.

/case-study lint validates every case study; /case-study practice <name> scaffolds a practice page the same way.

Stdlib + PyYAML; runs in a small GitHub Actions workflow on PRs (.github/workflows/lint.yml) — Pages still builds the site natively, this only adds a check.

Why a skill and not just a template

  • The hard part isn't the Markdown — it's surveying a repo and tying every claim to a path. That's what I did by hand for this plan (§01–§03) and it's exactly the repeatable part.
  • It keeps the rubric honest: the skill can't rate a row ● without a proof path the lint can find.
  • Dogfooding it on the three production apps (D9) means the template is proven before a fourth system ever exists.
  • It's a practice in its own right — the ways-of-working page can show the toolchain end to end: Lavish plan → /case-study → lint → no-mistakes → merge → Pages deploy.

Skill format follows the existing ones in ~/.claude/skills/ (lavish, no-mistakes): front matter with name, description, user-invocable: true, then the workflow.
