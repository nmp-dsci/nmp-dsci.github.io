01 · the skill on display

The page argues one thing: an agent was built, tested, and improved through evaluation, and each step left evidence

You said the core skill a visitor should take away is that you can build AI agents and run an evaluation loop that makes them production-ready: initialise, test, improve over time. DABstep is the cleanest demonstration of that in the portfolio, because the whole repo is that loop and nothing else. Every section of the case study maps onto one of the three verbs.

Build — one agent, one tool, two editable files

Haiku 4.5 through the Agent SDK with a single stateful execute_python tool. Each version is a folder: agents/vN/system.md, agents/vN/helper.py, and a frozen agent.yaml. The v0 prompt is NVIDIA's inference prompt, nine lines.

Case study §2 · rubric R4 · src/dabstep_loop/agent/

Test — the leaderboard's own scorer, a fixed split, a gate

The DABstep scorer is vendored verbatim and never edited. Ten gold tasks are the only thing scored; the 450 are locked behind a confirmation. A one-sided exact McNemar test on per-task flips decides promotion, and CI re-scores the champion from its committed results on every push.

Case study §3 · rubric R1, R3 · src/dabstep_loop/eval/, tracking/gate.py

Improve — one Sonnet session per cycle, and a ledger of what it did

The optimiser reads every failed trace, may write only into agents/v(N+1)/, and must leave a diagnosis.json. Cycle 1 fixed five and broke one, so it was held. A reflection pass found why. Cycle 2 kept the helper, removed one function, added two, and was promoted.

03 · the caveats that ride with the number

Five things the page has to say next to 9 of 10, or the number is marketing

P7 on the presentation rubric, and the argument the site exists to make. Each of these sits adjacent to the number it qualifies, not in a footnote.

n = 10. The gold split is ten tasks. The gate is blunt by construction: five fixes and no break is the smallest result that clears α = 0.05 (p = 1/32). The repo's own docstring says so; the page quotes it.
The 450 are unscored. This build never runs the leaderboard split; eval --split all is behind a confirmation and no answer key is derived from anyone's submission. NVIDIA's 87.5 / 90.0 is context for scale, not a comparison.
One day. All 13 commits and all three runs are dated 2026-09-14. The loop ran twice. "Improves over time" is shown across two cycles, not months. The deep page's cycle log is where that grows.
Task 2697 never passed. Three versions, three misses on the same hard task; cycle 2's diagnosis records "not found" rather than a guess. The flip chart shows it as the one grey column.
v2 is measured against v0. Because v1 was held, the champion stayed v0, so v2's five fixes are the same five v1 found. What v2 added is the unbroken 1871, which is the whole difference between p 0.109 and p 0.031.
The python tool is not a sandbox. exec() in-process with a timeout, output truncation and a loop-breaker. The demo image cannot make model calls, so the public surface is safe, but R5 stays partial.

05 · the structure, distilled from the three case studies

The spine is already a contract: seven H2s, a front-matter schema, two layout figures, and a lint that fails on all of it

You asked for the structure to be distilled so DABstep can reuse it. It is already executable. What follows is the shape every published case study shares, read from _templates/project.md, scripts/lint_case_study.py and the ConvFinQA page, which is the most recent and most complete of the three.

Front matter — what the home page, the matrix and the nav read

  • Three card lines, written last. headline ≤ 9 words and not the title; outcome one sentence ≤ 25 words; proof_line one sentence carrying a number with its baseline.
  • sections: seven one-sentence summaries ≤ 24 words, one per H2, rendered in the reading rail. They are the argument for a scanner who reads nothing else.
  • skills: keys from _data/skills.yml only, each with a proof sentence ending in paths.
  • production.live: true + production.order is what adds the system to the home matrix, the #work rows, the nav dropdown and the footer tree. No list to maintain.
  • production.rubric nine rows in _data/rubric.yml order; every non-shipped row a reason ≥ 40 chars; every row proof paths that must exist under --repo.
  • Two SVGs at _includes/diagrams/agent/<slug>.svg and topology/<slug>.svg, plus optional loop_diagram and home_diagram.

Body — assertion headings over figures, in impact order

  • Every H2 is label + em dash + claim ≤ 10 words. The label matches the spine exactly; the claim carries the number.
  • Order: outcome, visual, mechanism, setup. §1 leads with the result and its caveat; §2 opens with fig-agent.html; §4 with fig-topology.html; §7 is empty and the layout renders it.
  • Each claim gets a .slide: H3 assertion → fig-title → chart → three or four question-and-answer bullets the chart cannot say. Raw HTML inside, so <code> not backticks.
  • Budget 1,800 body words, no paragraph over 80, enumerations as lists or tables. Mechanism that pushes it over moves to the deep page, not out.
  • Never draw a number that is not in a repo. Charts live in _includes/diagrams/chart/ and follow the .dia class contract with a <title> in every <g>.
  • Deep page at _deep/<slug>/<name>.md: Setup → One cycle → Gate & promote → Cycle log → What changed since. The case study links down; the matrix never reads from it.

09 · five decisions before code

These change what gets built; everything else above is a default I will take

D1 · The repo has no GitHub remote blocker

links.repo is required, the lint infers --repo from its last path segment, and the repo link is on the card. Only the local no-mistakes mirror exists today.

D2 · Where DABstep sits on the home page

production.order sorts the matrix column, the #work row, the nav and the footer together.

D3 · The three practice pages say "In the three systems"

That H2 label is lint-locked, so folding DABstep in touches the template, the script, three pages and one hand-drawn chart. It is a second piece of work of similar size to the case study.

D4 · A deep page for the loop

The optimiser's prompt contract, the write guard and checksum, the ledger schema and the three-row cycle log do not fit 1,800 words. A deep page is where "improves over time" keeps growing as cycles are added.

D5 · R2 judge: na or partial

No judge exists and none is needed for exact-match answers. na says "not needed by design"; partial would read as a gap. Either way the score is 6 / 9, since only shipped rows count.

Anything else

Headline wording, a chart you would rather see, a claim you think the repo cannot support.

The same path the other three took: fill, score, draw, lint, build, review, gate

Risks I can see

  • The matrix at four columns on a phone. DESIGN.md forbids a side-scrolling matrix; short: abbreviation was designed for three. Needs a look at 400 px before the PR.
  • One day of history. "Improves over time" rests on two cycles dated the same day. The page says so; the deep page's cycle log is the fix over time, not wording.
  • Practices out of step if D3 is two phases: the home page will say four while the practices say three until the follow-up lands. Acceptable for one branch; not for long.
  • Proof-path drift. runs/*/traces/*.json globs resolve today; if run folders are ever pruned the lint fails, which is the intended behaviour.

not in scope, on purpose

Scoring the 450. Adding a judge. A third loop cycle. Any change to the rubric or the presentation lint. A new skill key in _data/skills.yml — the seven proposed all exist.
