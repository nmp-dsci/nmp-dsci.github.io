03 · the spike

The built DABstep page renders inside Lavish with its own fonts, CSS and all seven diagrams

Lavish serves one file and its sibling assets; it cannot follow the site's root-relative /assets/… paths. So the question was whether a rewritten copy of a built page is still the page. It is.

what was done verified 2026-09-17

cp -R _probeout/assets .lavish/review/assets
sed -e 's#"/assets/#"assets/#g' \
    -e 's#href="/\([^"]*\)"#href="http://127.0.0.1:8790/\1"#g' \
    _probeout/projects/dabstep-loop/index.html \
    > .lavish/review/dabstep-loop.html
npx -y lavish-axi .lavish/review/dabstep-loop.html

Then a headless check of the served copy: h1 "Two loops improve one agent…", svg.dia × 7, IBM Plex Serif loaded, body background #F7F6F2, zero failed requests.

what it tells us

  • No new tooling. The loop you already use for plans works on the site's pages as they are built.
  • One page per session. Lavish reviews a file, not a site. Internal links point at the local server on :8790, so a click opens the real neighbour page outside the review surface — fine for reading, no pins there.
  • Assets are 22 MB. The copy step needs to skip video/, dash/ and the ConvFinQA screenshots, or symlink instead of copy.
  • Analytics stripped. The gtag script is removed from the review copy so a review session is not a page view.
  • Two windows conflict. Lavish keeps one live view per session; if I open the session URL myself, yours is invalidated. I verify with headless Playwright instead (already the rule in memory).

04 · options

Ship Lavish now; spike the artifact route second, because it is the only one that refreshes a tab I did not open

ALavish over the built page recommended

A make review PAGE=projects/dabstep-loop target that builds, rewrites, copies assets and opens Lavish; a /review skill that runs it, polls, edits source, rebuilds and replies.

  1. 1build → export the page to .lavish/review/<slug>.html
  2. 2lavish-axi opens it; I poll
  3. 3you pin, note, send
  4. 4I edit source, rebuild, re-export, reply — Lavish reloads the revision
  5. 5Send & End → lint, audit, commit, /no-mistakes

Cost: ~60 lines of script + one skill file; one page at a time; the review copy is a rewritten build, not the deploy.

rendering verified reload-on-revision to confirm in first use

BClaude artifact with comments

Publish the page privately on claude.ai as a single inlined file. You comment in the artifact's own sidebar; a thread sent to Claude wakes this session; a republish updates every open view in place.

  1. 1build → inline CSS, fonts and SVGs into one file; strip the head skeleton
  2. 2Artifact publish → private URL, session watches it
  3. 3you comment, "Send to Claude"
  4. 4session wakes, I edit source, rebuild, republish; open tabs refresh

Cost: a second export path (inline everything, ~16 MB cap, fonts as data URIs); the page lives on claude.ai, not localhost; works from your phone. Unverified end to end.

06 · risks and what is not solved

Four things to know before the first session

Reload behaviour

Lavish reloads on a new revision of the file — that is how the s10 fixes appeared for you — but a rebuilt page is a bigger diff than a plan edit, and whether pins survive a reload is not yet verified. First session answers it.

Home page and matrix

The export handles any built page, home included, but the home row's container query and the dropdown JS come along as-is; study.js is copied with the assets so the nav and theme toggle work.

The lint still decides

A comment that asks for an eleventh word in an H2 claim, or a number without a source, gets a reply saying why not, not a silent edit. The review loop sits inside the contract, not beside it.

Option B is the better loop if it works

It refreshes a tab I did not open, wakes the session without a poll, and works away from the desk. It is second only because it is unverified and the page would live on claude.ai. If A's reload disappoints, B is next.
